## 专家一：Kimi-k3 评审意见摘要

### 1. 致命工程死穴
- **夜间睡眠回放是不可逆的垃圾放大器**：若白天零深层写入意味着零质检，草稿池堆满碎屑，夜间交由大模型批量摘要，极易引入新幻觉（把闲聊误当定案）。
- **Save-time 冲突检测仲裁死锁**：若写入时同步调用大模型仲裁，会拖慢白天交互链路；若新事实覆盖旧事实，未定义下游依赖的级联失效规则。
- **PPR 能量扩散天然带有热搜偏见**：PPR 倾向于度数高的节点，如果讨论过的旧方案连线多，PPR 会把作废方案顶到最前。

### 2. 选型建议
- **坚决弃用 KùzuDB，深耕 SQLite**：KùzuDB 处于 0.x 阶段，API 变动频繁，单机万级节点 SQLite CTE 递归查询和 Python 稀疏矩阵迭代完全足够。

## 专家二：Claude Haiku-5.5 评审意见摘要

### 1. 核心裁决
- **双时态与 Living State 的语义边界**：现役真理与历史演进必须物理隔离，双时态必须在存储层强制执行 `invalid_at IS NULL`，PPR 必须只在有效子图上运行。
- **相变打标的降级防线**：在自然语言里靠实时分类器判定“拍板”极度脆弱，应降级为“会话打候选标 + 夜间睡眠确认”。
- **禁止物理删除**：夜间折叠绝不能物理删除白天日志，必须做只读冷归档，保留 100% 的悔棋与回滚能力。

### 2. 性能与落地
- 入库仲裁必须是轻量确定性规则，禁止在实时交互链路上串行阻塞大模型调用。

## 结论与采纳清单

方案书已根据上述评审意见完成如下重大修正：
1. **[采纳]** PPR 计算前强制下沉“有效子图切片（Active Subgraph Slice）”，断开失效边；
2. **[采纳]** 夜间睡眠执行“冷归档存盘”而非物理抹杀；
3. **[采纳]** 引擎保持 SQLite 单文件，不引入 KùzuDB；
4. **[采纳]** 白天相变检测由 Drex-Max 充当轻量候选打标器，平滑解耦。
